Design editors an agent can drive

Figma alternatives where an agent running in bb — on this Fedora/Nobara machine — can read the design, edit it, and turn it into code. Ranked by what actually matters: the agent surface, Linux support, and licence.

2026-09-27 Nobara 44 · KDE · Fedora family bb providers: codex · claude-code · pi · opencode Full evidence: 04-design-editor-options-agent-driven.md

01Verdict first

Three viable picks and one category change. The rest of the field is either art tooling, abandoned, or has no agent surface at all.

Pick this

OpenPencil

MIT · native Linux · .op JSON · op CLI + MCP + headless

The only candidate that can design and export with no GUI, no account, no cloud. A bb agent designs headlessly, writes git-diffable .op files, then runs codegen to React, Vue, Svelte, Flutter, SwiftUI, Compose, or React Native.

  • .deb / .AppImage, single Rust binary
  • op start --headless --file design.op
  • Model tiers tuned for small / local models
Best canvas

Brilliant

Proprietary · browser on Linux · .bl text · MCP free

The most agent-native editing experience here — and its MCP-driven agent use is unlimited even on the free plan. Workspaces are plain folders of .bl Blueprint text, so designs diff in PRs.

  • No Linux desktop build — Chromium/Firefox only
  • Local MCP bridge via npx -y @brilliant-hq/mcp
  • Figma import; React/HTML/SVG/PDF export
Open + self-hosted

Penpot

MPL-2.0 · self-host · official MCP via browser plugin

The mature, fully open option. Run it with Podman/Docker, connect the official MCP server through a plugin in the browser tab, and the agent works on your own instance.

  • Heaviest setup of the three
  • Plugin tab must stay open
  • No plain-text design file for the agent
Category change: Onlook (Apache-2.0, Linux .deb/.AppImage) doesn't export code from a design — it edits a real Next.js + Tailwind codebase directly. If the project is already React, the code is the design and there is nothing to translate.

02The one distinction that matters

Family matters more than the feature list. Two corollaries follow from it.

Design-as-text

The design is a file on disk that the agent reads and writes like code.

OpenPencil Brilliant Onlook

  • Works with any bb provider — even one without MCP
  • Git diff, branch, review, blame
  • Reading needs no running app

Design-in-a-service

The design lives in an app or database; the agent goes through MCP or a plugin API.

Penpot Figma

  • Needs an MCP-capable provider (Codex / Claude Code / OpenCode)
  • The app and the bridge must be running
  • Richer live editing, weaker git story
Corollary 1. If the agent drives the tool over MCP, the tool's built-in AI is irrelevant — the model doing the work is bb's provider model, local or cloud. "Does it support Ollama?" only matters for the app's own chat, not for a bb workflow.
Corollary 2. Export fidelity is a spectrum: OpenPencil/Brilliant translate a design file to code; Onlook never separates the two.

04The four candidates in detail

OpenPencil

MIT · Rust · created 2026-02 · 6.0k ★
native Linuxheadless .op JSONMCP + CLI 8 code targets

Why it wins here

  • Two agent doors, both local: the op CLI (op design, op insert, op export, op codegen:*) and an MCP server (op-mcp) over stdio or HTTP.
  • op start --headless --file design.op — a windowless, file-backed MCP server, so a bb worktree needs no GUI at all.
  • op install --target codex installs the official agent skill; one-click MCP into Claude Code / Codex / OpenCode / Kiro / Copilot.
  • Local models are a first-class case: "basic-tier" models (Qwen, Llama, Mistral, MiniMax) get simplified prompts, and source confirms local Ollama/vLLM base URLs.

Caveats

  • Young — first release Feb 2026, v0.8.4, effectively one primary author.
  • GUI is a native Rust/GPU app (no Electron), so it won't feel like Figma on day one.
  • Chinese-ecosystem integrations (sponsors, Anthropic-format passthrough for Kimi/GLM/DouBao) — harmless for the CLI/MCP path.

Brilliant

proprietary · browser on Linux · beta
no Linux desktop buildMCP free .bl text filesFigma import

Why it's worth it

  • The most polished agent-native canvas: built-in chat, external-agent MCP, per-turn revert, quality linter.
  • MCP-driven agent use is unlimited on every plan, Free included — only the in-app chat is capped (10 msgs/day with your own AI on Free).
  • A workspace is just a folder; canvases are .bl text. "No hidden project database" — git branch, PR review and git blame work on designs.
  • One-time local bridge for the web tab: npx -y @brilliant-hq/mcp, a stdio↔loopback router. Design data never leaves the machine.

Caveats

  • Closed source, no self-host, account required.
  • Browser-only on Fedora (Safari unsupported); Chromium 147+ asks for local-network permission.
  • MCP needs the tab + bridge running; the GUI can't be fully headless.

Penpot

MPL-2.0 · 60.4k ★ · the mature open option
self-hostofficial MCP plugin bridgeno text files

Why choose it

  • The only fully open, self-hostable, battle-tested Figma alternative of the group.
  • Official MCP server now lives in the main repo (penpot/penpot/tree/develop/mcp); the standalone repo was archived when it was merged.
  • Works against your own instance — no cloud dependency, no proprietary components.

Caveats

  • Heaviest setup: self-host + plugin server :4400 + MCP server :4401 + a plugin tab that must stay open.
  • Node ≥ 22 and npm run bootstrap.
  • No plain-text design file — an agent without MCP cannot read the design at all.

Onlook

Apache-2.0 · 26.8k ★ · code-as-design
native Linuxzero translation loss Next.js + Tailwind only

Why it's different

  • "The Cursor for designers": a visual editor operating on a real Next.js + Tailwind codebase.
  • The agent surface is the repository itself — bb edits the same files, Onlook is the human GUI on top.
  • No MCP, no export step, no drift between design and code.

Caveats

  • Framework-bound by design (Next.js + Tailwind).
  • Not a design artifact — nothing to hand to a designer as a file.

Can OpenPencil round-trip back to Figma?

Short answer: no native .fig export. op import:figma design.fig is import-only, and Figma's importers don't read .op. Four lossy routes back:

RouteSurvivesLost
SVG export → paste / drag into a Figma file best editable
desktop app export dialog only — CLI/MCP exports are png/jpeg/webp/pdf		 vectors, fills, strokes, text, groups auto-layout, components/variants, variables/tokens, constraints. Figma's own docs call SVG the lossless cross-tool format — it is still a snapshot.
HTML+CSS export → html.to.design plugin screens rebuilt as frames, with auto-layout heuristics exactness; third-party plugin
PNG / JPEG / WebP / PDF pixels all structure — review only
op export-deck --format pptx → Figma file browser slide content (Figma imports .pptx) anything outside the deck boards
A true round trip needs a small Figma plugin that reads .op (documented JSON) through the Plugin API — nobody has built one. Brilliant has the same shape (imports from Figma, exports React/HTML/SVG/PDF) and Penpot imports SVG, not .fig. So "design in an open tool, finish in Figma" always means a lossy SVG/code hand-off, never a file interchange.

05Wiring it into bb

The constraint that shapes every recipe: MCP lives in the provider CLI, not in bb core.

bb facts

  • Providers on this machine: codex, claude-code, pi, acp-opencode, acp-cursor, acp-omp.
  • MCP-capable: Codex (config.toml), Claude Code (claude mcp add), OpenCode (opencode.json) — stdio and streamable HTTP.
  • Pi has no MCP client. A pi thread reaches a design tool through the shell (op, curl) or through the design file itself.

Local models

  • bb has no "local" provider id — the local model is configured inside the provider CLI you pick.
  • Pi: ~/.pi/agent/models.json with an OpenAI-compatible baseUrl (Ollama :11434/v1, LM Studio, vLLM, SGLang), or GGUF models via the llama.cpp router (/llama).
  • OpenCode: its own provider config.
  • Small models struggle with long design trees — OpenPencil is the one tool that ships prompt tiers for exactly this.
A — OpenPencil recommended first try 
# 1. CLI only (no GUI needed) — usable from a bb worktree
curl -fsSL https://raw.githubusercontent.com/ZSeven-W/openpencil/main/scripts/install-op.sh | bash
# or grab OpenPencil-*-x64-linux.AppImage / .deb from GitHub Releases

# 2. design headlessly, file-backed
op start --headless --file design.op     # windowless MCP server on a file
op design @landing.txt                   # batch design from a DSL file
op export --output hero.png --format png

# 3. code out
op codegen:plan <plan.json> ; op codegen:assemble <planId> --framework react
op install --target codex                # install the OpenPencil agent skill

Then either let the bb agent call op directly (works on every provider, including pi), or register the MCP server with a Codex / OpenCode / Claude Code thread — stdio via the desktop binary with --mcp design.op, or HTTP at http://127.0.0.1:<port>/mcp.

B — Brilliant best canvas
  1. Open brilliant.design in Firefox or Chromium on Fedora and sign in.
  2. Register npx -y @brilliant-hq/mcp as the MCP server (or http://127.0.0.1:3333/mcp if you ever run the macOS/Windows app) in the Codex / OpenCode / Claude Code config of a bb thread.
  3. Keep the workspace folder inside the repo so .bl files land in git — a pi thread can then read and patch them as text, no MCP required.
C — Penpot self-hosted fully open
  1. Self-host Penpot with Podman/Docker compose and open the UI in a browser.
  2. From penpot/penpot/mcp: npm install && npm run bootstrap → plugin server :4400, MCP server :4401.
  3. Load http://localhost:4400/manifest.json as a plugin in the Penpot tab and click "Connect to MCP server"; keep the plugin UI open.
  4. Point the bb provider at http://localhost:4401/mcp (stdio-only clients: npx -y mcp-remote http://localhost:4401/sse --allow-http).
D — Onlook if the project is already React

Point Onlook at the project directory; humans tweak visually, bb agents edit the same files. No bridge, no export — and no design artifact to keep in sync.

Keep this repo's tokens authoritative. design-system/tokens.json + tokens.css already exist. OpenPencil's design variables generate CSS custom properties (var(--name)) in code output; Brilliant's Styles/default.ds emits a resolved .gen.yaml that Style Dictionary and build scripts read. Either way: this repo is the token source of truth, the design tool is a consumer.

06Decision checklist

Write or only read?Does the agent need to author designs, or just consume them for code?
Diffable in PRs?Must the design file be reviewable in git, or is a binary/service file fine?
Which provider runs the thread?Codex/OpenCode/Claude Code can take MCP; pi needs the CLI or the file.
GUI in the loop?Is a running app acceptable, or must the pipeline be headless in a worktree?
